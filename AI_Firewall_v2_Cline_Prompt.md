# Cline: новый проект AI Firewall v2.0 — разработка с нуля

Ты — ведущий архитектор и Python/backend-разработчик системы корпоративной ИБ. Начни **абсолютно новый проект AI Firewall v2.0**. Не импортируй, не копируй и не сохраняй код, Docker-конфигурации, решения и временные обходы из прошлых версий AI-Fire / ai-firewall-starter. Техническое задание — прилагаемый документ `AI_Firewall_v2_Architecture.docx`; его требования приоритетнее предложений из старых переписок.

## Цель
Open WebUI — единый видимый веб-интерфейс сотрудников. Проверять текст, изображения и файлы **до любых постоянных записей в Open WebUI**, до индексации/RAG и до передачи в LiteLLM/LLM. Персональные данные, коммерческая тайна, секреты и запретные документы должны блокироваться или маскироваться по правилам. Ответы проверять **до сохранения**. Исходные значения для разрешённого обратимого маскирования хранить только в отдельном зашифрованном PII Vault; демаскировать только в доверенном представлении для авторизованного пользователя, не записывать восстановленный ответ в Open WebUI.

## Ограничения
- Локальное развёртывание Docker Compose; Python/FastAPI для собственных служб.
- Только свободные/открытые компоненты по возможности; для каждого компонента проверь лицензию и ограничения.
- Работа на русском языке, российские ПДн и локальные корпоративные правила.
- Существующая LLM доступна по OpenAI-совместимому API, запускать собственную LLM в Compose не требуется.
- LiteLLM — единственный AI API Gateway; n8n/Tool Gateway сейчас **не реализуем**; оставь расширяемые контракты.
- Не писать новый чат с нуля: модифицировать контролируемую фиксированную версию Open WebUI; допустим собственный fork. Не полагайся на Filter Function как доказательство контроля pre-save.
- Не использовать реальные ПДн в тестах. Никогда не исполняй код из входящих промтов и файлов.

## Обязательная архитектура
1. **Protected Open WebUI**: модифицированные обработчики для создания/редактирования/сохранения чатов, загрузок, предпросмотра и RAG. Любой вход до сохранения вызывает доверенный Privacy Gateway; клиентская проверка — только UX, не основная граница безопасности.
2. **Privacy Gateway** (FastAPI): приём текста/вложений, карантин, вызов детекторов и Policy Engine, выдача короткоживущего проверяемого admission token, привязанного к пользователю, операции, содержимому (hash), сроку и версии политики.
3. **DLP Policy Engine**: решения `BLOCK`, `REVIEW`, `MASK`, `ALLOW`; приоритет строгой политики; fail-closed. Администратор может менять глобальное принятие ПДн и коммерческой тайны, категории документов, политики по группам, словам, regex, словарям, эталонам, изображениями и TTL. Сохраняй версии правил и аудит без payload.
4. **PII Detection**: Presidio, Natasha, свои regex/контрольные суммы для РФ. Измеряй качество на синтетических русских сценариях.
5. **Document inspection**: изолированный карантин, MIME magic, PDF/DOCX/XLSX/TXT/JSON, OCR ru, метаданные, маркировка, ClamAV, YARA-X, ограничение ресурсов и архивов, блокировка нераспознанного и шифрованного контента. Эталонные документы: SHA-256, фрагментные отпечатки; изображения: OCR/pHash (без обещаний гарантии).
6. **PII Vault**: отдельный Postgres, AEAD-шифрование (AES-GCM либо другое строго обоснованное), ключи в OpenBao/KMS, случайные scoped tokens, TTL (например 1ч, 24ч, 7д, 30д), ограничения по пользователю/чату, удаление и журнал без секретов. LiteLLM/LLM/Open WebUI не должны иметь доступа к БД Vault и ключам.
7. **LiteLLM + Security Gateway**: прокси к уже существующей локальной LLM, второй рубеж проверки Prompt Injection, jailbreak, вредоносных конструкций Python/PowerShell/Bash/JSON, секретов и небезопасного ответа. Не возвращать демаскированные значения в Open WebUI.
8. **Изоляция**: отдельные Docker-сети и роли БД; секреты вне git, HTTPS и аутентификация до использования реальных данных; структурированные логи без исходных промтов.

## Критические инварианты (должны быть проверены тестами)
- Сырые ПДн/коммерческая тайна не сохраняются в БД, RAG, файлах, экспортных данных, кэшах и логах Open WebUI или LiteLLM.
- Проверяемый исходный запрос допускается в память доверенного ingress на время анализа. Не утверждать, что он вообще нигде не появляется: тестировать отсутствие персистенции и границы передачи.
- Direct API calls не обходят проверку: server-side enforcement, не только JS/UI или LiteLLM guardrails.
- Запрещённый документ не попадает в модель/индекс/хранилище.
- При отказе любого обязательного детектора — `BLOCK`; если формат неизвестен — `BLOCK`/`REVIEW` в защищённом карантине.
- Декодирование токенов возможно только при аутентификации, привязке к контексту и до TTL. Ответ для хранения содержит только токены.
- При незащищённом streaming сохранить блокирующий buffered/non-stream режим; отключить неподдерживаемые вложения, RAG, tools и endpoints до покрытия.

## Порядок работ
**Начни с планирования и доказательства архитектуры**, а не с написания десятков контейнеров:

1. Создай чистую структуру репозитория, README, threat model, ADR по выбранной версии Open WebUI и карте эндпойнтов, которые могут сохранять/индексировать вход. Изучи её исходники; перечисли места записи BEFORE/AFTER проверки и обходные пути.
2. Составь граф потоков данных и предложи минимальный POC: однострочный текст → pre-save sanitization → Open WebUI DB только с токеном → LiteLLM → LLM → output check → UI-only deanonymization.
3. Создай Docker Compose, `.env.example`, healthchecks, раздельные сети и базовые сервисы, не включая n8n.
4. Реализуй pre-save enforcement в Open WebUI и Privacy Gateway; сначала тесты прямого API, истории и логов на синтетических canary strings.
5. Добавь Presidio/Natasha и настраиваемые DLP-политики; отдельный PII Vault/ключи/TTL.
6. Реализуй защищённое восстановление только для отображения и output scanning до DB.
7. Подключи анализ файлов и DLP fingerprints, затем LLM Guard/проверку кода.
8. Реализуй минимальное админское API/UI политик (TTL, режимы ПДн/коммерческой тайны, словари, образцы, версии и публикация).
9. Проведи pytest/integration/e2e/fault-injection и проверку PostgreSQL/Redis/RAG/файлов/логов на наличие тестовых canary-значений; подготовь отчёт о покрытии и рисках.

## Формат первой итерации
До массового написания кода выдай краткую техническую записку: (а) границы доверия, (б) какой fork/version Open WebUI и почему, (в) реальные точки сохранения из исходников, (г) план минимального POC, (д) список угроз и способов тестирования, (е) структуру репозитория. После этого реализуй первый небольшой вертикальный срез и запусти его тесты. Если Docker, интернет или LLM API недоступны — не выдумывай успешный запуск; отделяй проверенное от предположений.
